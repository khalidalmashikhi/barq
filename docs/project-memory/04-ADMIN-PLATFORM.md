# 04 — Admin Platform

## Current state

**Corrected 2026-07-27** — the previous version of this section ("exactly one real admin capability") was stale and contradicted by the actual repository; repository code is the source of truth where memory conflicts with implementation.

Real, state-changing admin CRUD exists across most of the marketplace: Providers (create/edit/approve/publish/unpublish/archive), Services (create/edit/publish/unpublish/archive), Prices (create/update/deactivate), Availability (create/edit/activate/deactivate), Bookings (list/detail/cancel — reuses the shared booking lifecycle engine with `actorType: "ADMIN"`, not a parallel state machine), Categories (visibility-state management, subcategories), Feature Flags (global on/off), and Homepage Sections (visibility + ordering). `src/lib/admin/` has ~70+ files; every query/action calls `requireAdmin()` itself in addition to `admin/layout.tsx`'s own gate (defense in depth, not redundancy).

**Admin Operations Platform phase (2026-07-27) added, on top of the above, without redesigning any of it:**
- **A real Overview dashboard** at `/admin` (`getAdminOverview()`), replacing the previous bare redirect to `/admin/providers`: platform metrics (total customers/providers, published services, booking-status breakdown, total vs. PUBLISHED review counts + PUBLISHED-only average rating, Completed Gross Revenue kept separate per currency, database connectivity via a real `SELECT 1`), operational queues (pending provider approvals, bookings awaiting provider, bookings in progress, recently cancelled in the last 30 days, recent reviews), and Provider/Customer operational insight lists (recently joined providers; providers without services; providers with no completed bookings; providers with no recent booking activity — no CONFIRMED/IN_PROGRESS/COMPLETED booking with `updatedAt` in the last 30 days; recently registered customers; customers with most bookings; customers awaiting reviews — reusing the customer-side COMPLETED+no-Review eligibility rule, not re-deriving it).
- **`/admin/customers`** (list + minimal detail) — the first admin-facing Customer surface. Read-only: no create/edit/status action exists, since a Customer profile is created only through self-service. Phone number is the only display identity (no name/email/avatar field exists anywhere in the schema).
- **`/admin/reviews`** — the first admin-facing Review surface, **read-only by design**. The schema's `ReviewModerationState` (PUBLISHED\|FLAGGED\|REMOVED) is filterable here because the column is real, but no flag/publish/remove action exists on this page or anywhere else — nothing in the codebase currently sets FLAGGED/REMOVED, so those filters honestly return empty results against real data today. No moderation workflow or review-lifecycle change was introduced.
- Cross-links between Provider/Service/Booking/Customer/Review detail pages, using `providerId`/`serviceId` filter params `getServices()`/`getAvailabilitySlots()`/`getBookings()` already accepted before this phase (the UI simply didn't construct links using them yet).

**Payment Experience & Financial Operations phase (2026-07-27) added:**
- **`/admin/payments`** (search/filter list + a concise Payment Overview of counts-by-status and captured/refunded amounts by currency) and **`/admin/payments/[id]`** (full detail, incl. `providerReference` labeled "Gateway Reference," the linked Invoice when one exists) — both reuse the pre-existing `get-payments.ts`/`get-payment-detail.ts` (the latter additively extended, not rewritten). **Read-only by design**: `capture-payment.ts`/`refund-payment.ts` already existed in the backend before this phase and remain completely unwired — no button, form, or action menu anywhere triggers either.
- The same phase also added a Customer-facing Payment History (`/payments`, `/payments/[id]`) and a Provider-facing Payment History (`/provider/payments`) — outside the admin surface, but sharing the same `PaymentStatus` presentation module (`src/lib/payments/payment-status.ts`) and the same read-only discipline.

**Still deliberately absent / out of scope:** Pricing-rule modes (admin/provider/both-with-approval/RFQ), commission models beyond the fixed 3-tier, translation review workflow, CMS/homepage *content* management (`HomepageSection`'s `visible`/`sortOrder` data is now genuinely read by the public homepage — corrected 2026-07-27, see below — but each section's own *content* stays hardcoded per-component; only 3 of 13 registry sections query real data), an audit-log viewer UI, support tickets, internal messaging, moderation/approval workflow for reviews, and — even after the Payment Experience phase — any admin UI trigger for capture/refund (those actions exist only in the backend, by explicit design) and any real Receipt entity (a "Payment Record" presentational view over existing Payment/Invoice data is not a persisted Receipt model).

**Growth Foundations phase (2026-07-27) — documentation correction only, no behavior change:** this file and `01-CURRENT-STATE.md` previously claimed the public homepage did not read `HomepageSection` data at all ("the public page still doesn't read it"). That was stale even before this phase — `src/app/[locale]/page.tsx` already called `getHomepageSectionRenderOrder()` and rendered from the real `visible`/`sortOrder` columns, gated by the `homepage_dynamic_sections` feature flag, since Phase 1.5. This phase found and corrected the claim; it changed no `HomepageSection` code or behavior.

## Guardrail

Per `11-SECURITY-POLICY.md`, admin-controlled configuration must never weaken authentication, payment integrity, or permission enforcement — those stay code-controlled regardless of how much of the above becomes admin-manageable. See BR-006 in `16-BUSINESS-RULES.md` for the permanent rule ID this maps to, and BR-001 for a real, verified enforcement gap (provider approval doesn't yet gate service publishing). For exactly which of `ADMIN`/`OPERATIONS`/`SUPPORT`/`FINANCE`/`CONTENT`/`MARKETING` can do what, per module, see `20-PERMISSION-MATRIX.md`.
