# 12 — Decisions Log

A running log of real, **granular/tactical** decisions made during implementation work — the "we chose X over Y for this specific reason" calls made *while building something*, in the spirit of `docs/08-governance/DEVELOPMENT_LOG.md`. Append to this file as new decisions are made — do not rewrite history in it.

**Scope split from `17-CHANGELOG-DECISIONS.md`**: this file is for implementation-detail decisions (a schema shape choice, an enum reuse, a file-organization call) made in service of a larger goal. `17-CHANGELOG-DECISIONS.md` is for the higher-level architectural/product decisions those tactical choices serve (a new ADR, a product-direction commitment). If a decision here was made *in service of* a `17-CHANGELOG-DECISIONS.md` entry, link to it rather than re-explaining the higher-level context.

## Entry format

```
### YYYY-MM-DD — Short decision title
**Context:** why this came up
**Decision:** what was decided
**Alternative(s) considered:** what else was on the table, and why it lost
```

### (project-memory phase) — Reuse `BookingActorType` for the new `AuditLog` model rather than a new enum

**Alternative considered:** A new `AuditActorType` enum — rejected as unnecessary duplication (DRY) since the existing enum's values are already generic actor-kind values despite its booking-era name.

**Decision:** New `docs/project-memory/` sits alongside the numbered directories, explicitly exempt from the ADR/RFC gate — update it freely as things are learned.
**Alternative considered:** Making it `docs/12-project-memory/` to match the numbering convention — rejected because that would visually imply it's part of the same versioned/frozen documentation register, which it deliberately is not.

### 2026-08-12 — Core Service Enrichment (Gate 3): `Service.regionCode` + `Price.pricingUnit` wired as domain read/write only
**Context:** Gate 2 (local commit `1fde9db`, migration `20260812120000_service_region_pricing_unit`, still UNAPPLIED) added two nullable columns: `Service.regionCode` (broad Oman **governorate** where a service operates — a discovery/filter facet) and `Price.pricingUnit` (the display basis of `amount`). Gate 3 wires application read/write for them **without any UI, Explore filter, or presentation change**.
**Decision:**
- Two isomorphic code registries were added as the app-level allow-lists: `src/lib/regions` (the **11** governorate codes, mirroring the Gate-2 DB CHECK exactly) and `src/lib/pricing-units` (**5** codes: `PER_PERSON, PER_BOOKING, PER_DAY, PER_HOUR, PER_TRIP`). Both follow the `service-types/registry.ts` convention (ADR-0015: String codes, not Prisma enums) and each exposes a `parseRegionCode`/`parsePricingUnit` three-state helper (`null` = unset, code = valid, `undefined` = invalid).
- `regionCode` is a **governorate-level discovery facet only** — NOT a location/geography system. There is deliberately **no** wilayat/city/map/lat-lng/meeting-point/route/PostGIS, and **no** Vehicle/Asset entity.
- `pricingUnit` is **display/commercial metadata ONLY**. It rides the *same* ACTIVE `Price` row as `amount`/`currency` in every reader and **does not affect totals or booking behaviour** — nothing multiplies by it, `Booking` was not touched, no `priceSnapshotUnit` was added, and `createBooking`/payment/refunds are unchanged. On update it is set via a metadata-only `updateMany` on the ACTIVE price(s) — never a new Price row (append-only price versioning preserved, no duplicate ACTIVE price).
- The DB intentionally has **no** CHECK on `pricingUnit` (commercially extensible), so `src/lib/pricing-units` is its *only* allow-list; `regionCode` keeps its DB CHECK as defence-in-depth.
- Invalid `regionCode`/`pricingUnit` reuse the existing `INVALID_INPUT` error (Gate-4 UI will be dropdowns, so an invalid value is a malformed/spoofed request) rather than adding new error codes + 8-locale i18n keys.
- Update semantics: for these freely-nullable fields, an **absent** form field leaves the value unchanged while a **present-but-empty** field clears it to NULL — deliberately different from `categoryId`'s "empty = leave unchanged" (a category is required at publish and must never be silently nulled). All readers/actions are NULL-tolerant for legacy rows; no backfill.
**Alternative(s) considered:** Dedicated `INVALID_REGION`/`INVALID_PRICING_UNIT` error codes (rejected: needs new codes + translation keys across 8 locales for a spoof-only path); mutating/versioning a new Price row to change `pricingUnit` (rejected: it is metadata, not a price change); giving `pricingUnit` a DB CHECK (rejected in Gate 2 for commercial extensibility).

### 2026-08-12 — Core Service Enrichment (Gate 4): region/pricing-unit UX, public presentation, and the governorate Explore filter
**Context:** Gates 2/3 made `Service.regionCode` and `Price.pricingUnit` exist and be read/written by the domain (local commits `1fde9db`, `9d55c6c`). Gate 4 makes them useful to providers, admins, and customers without disturbing any invariant.
**Decision:**
- **Labels centralized in the `common` i18n namespace** (`governorate.*`, `pricingUnit.*`, `priceWithUnit`), added to **all 8 locales**, with code→key bridges `src/lib/regions/labels.ts` + `src/lib/pricing-units/labels.ts` (`as const satisfies Record<...>`, mirroring `SERVICE_TYPE_LABEL_KEYS`). The registry stays authoritative for validity; i18n for labels. This is the ONE place a code becomes a label — no per-surface switch (item 12). `regionLabelKey`/`pricingUnitLabelKey` fail safe to `null` for unknown/absent, so presentation never leaks a raw code (item 21) — the only guard for `pricingUnit`, which has no DB CHECK.
- **Shared field components** `RegionField` + `PricingUnitField` (async server components consuming the registries + `common` i18n) — native `<select>`s that submit the stable CODE and display the localized name, reused across provider create/edit + admin create/edit. No governorate/unit list is duplicated in any form.
- **Admin surface honesty (item 6):** admin *create* takes only `regionCode` (that path provisions no Price, so there is no unit target); the admin *edit* form shows `PricingUnitField` only when an ACTIVE price exists. Provider and admin share the same registries/validation.
- **Public presentation via the shared `ServiceDetailView`** (one component → public detail + provider preview + admin preview, no forking): a governorate tile (omitted when null) and price-with-unit via the `priceWithUnit` template. Public cards reuse the existing `ExperienceCard` contract — the server page resolves labels and passes ready display strings (governorate via the existing `location` slot, price+unit via `price`), so the client card gains no i18n/registry coupling.
- **Currency formatting left as-is:** price stays the pre-formatted `"25 OMR"` string produced in the query layer; Gate 4 only appends the localized unit. Migrating to `formatCurrency` is a separately-deferred concern (documented in `format-number.ts`) and out of scope here.
- **Explore governorate filter** on `/services`: `?region=<CODE>`, URL-addressable, validated against the registry (unknown → silently ignored, like an unknown `providerId`/`category`), added to `getServices` as a `regionCode` where-clause that **composes via AND** with the relational category filter and every other filter. No customer-facing `pricingUnit` filter (item 15) — region is the discovery facet; the unit is price-display metadata.
**Alternative(s) considered:** Duplicating governorate/unit labels into the `provider`/`admin`/`services` namespaces (rejected: DRY — one `common` home consumed everywhere); passing raw codes to the client card and resolving there (rejected: unnecessary client i18n coupling; the server resolves and passes strings); a new i18n namespace for governorates (rejected: `common` is already loaded everywhere, avoids wiring a new namespace into `namespaces.ts`/`types.d.ts`).

### 2026-08-15 — Provider Mutation API v1 (Gate PC): pre-auth wrapper, and standalone price mutation DEFERRED (no domain to adapt)
**Context:** Gate PC exposes the existing provider write operations (profile/service/availability/booking-action Server Actions) as thin `/api/v1/me/provider/**` JSON adapters for the native iOS client (ADR-0018). LOCAL commit `6520000` on `staging` — NOT pushed/deployed, VERIFIED BY TEST ONLY. Two decisions were forced during implementation.
**Decision:**
- **A pre-authenticating mutation wrapper (`withApiV1ProviderMutation`) was introduced** rather than reusing the read gate (`withApiV1Provider`). Every provider Server Action handles an unauthenticated session by calling `redirect("/")` (a browser-form convenience) — inside a route handler that throws `NEXT_REDIRECT` and emits a **307**, not a clean JSON **401**. The wrapper runs `requireProvider()` *before* invoking the action, so on no/expired session it returns 401 and the action is never reached (its redirect path is unreachable). It uses the LOOSEST gate (`requireProvider`, not `requireApprovedProvider`) so an APPLIED provider is admitted and then correctly told `PROVIDER_NOT_APPROVED` *by the action's own* stricter gate as a result code — never blocked at the wrapper (matching the web's own gating split).
- **Standalone provider price mutation is DEFERRED — because no provider price-edit domain exists to adapt.** The initial ACTIVE `Price` is created *bundled inside* `createService` (the provider's only price write), and `update-service.ts` explicitly records price-edit as "a distinct future decision, not made here" (Price is append-only/versioned). Exposing a price-mutation endpoint would require **inventing new domain logic**, which violates the thin-adapter mandate — so Gate PC exposes price only at service creation and adds no price-mutation route. Also deferred (same "no safe existing domain to thinly adapt within this gate" reasoning): verification-document upload (multipart + storage orchestration already owned by `/api/provider/documents`), provider media (Supabase Storage still inert), and provider application/resubmission (distinct onboarding concern; `applyAsProvider` targets users with *no* provider, incompatible with the provider-mutation gate). **Provider payments/payouts: NOT STARTED.**
- **The shared provider auth-error → envelope mapping was extracted into one pure, server-only-free module (`provider-auth-error.ts`)** now used by BOTH gates — statically testable against the real error classes, which also root-fixed the `ForbiddenError` class-field `instanceof`-across-mock-boundary test failure. Ownership stays at the domain boundary (no client `providerId`; missing/not-owned → uniform 404); success re-reads via the existing ownership-scoped GET reader and returns the existing DTO (no raw Prisma objects). Mutations are test-verified, **not** live-QA'd in this gate.
**Alternative(s) considered:** Reusing the read gate and catching `NEXT_REDIRECT` to synthesize a 401 (rejected: brittle — depends on Next's internal redirect error shape; pre-auth is explicit and robust). Adding a provider price-edit endpoint that inserts a new versioned Price row (rejected: that price-versioning semantics is an un-made domain decision — building it here would be new business logic, not a thin adapter). Building a JSON/multipart document-upload twin of `/api/provider/documents` (rejected: duplicates upload orchestration; infra live-status also unconfirmed).

### 2026-08-15 — P0-1 security gate: authoritative server-side Oman phone canonicalization before OTP
**Context:** The Full Platform Audit flagged P0-1 — OTP send accepted the raw client phone string with no server-side normalization or country restriction, while Twilio is live on staging. Consequences: SMS-pumping/toll-fraud to arbitrary international numbers, per-number cooldown/daily-cap bypass via format variation (`+96890…`/`96890…`/`0096890…`/`98…` are distinct identifier strings), and identity fragmentation (`User.phoneNumber` unique on the exact string). Scope: close ONLY P0-1 — not an auth redesign, no durable/IP limiter (separate P1).
**Decision:**
- **One authoritative normalizer** `src/lib/otp/normalize-oman-phone.ts` (pure, no I/O, no logging) canonicalizes every accepted Oman representation to `+968XXXXXXXX` (8 national digits) and REJECTS wrong lengths, non-digit input, and any explicit non-`+968` country code — never silently coercing a foreign number to Oman. Accepted: bare 8 digits, `+968…`, `968…` (11 digits), `0096898…`, plus spaces/dashes/parentheses/dots.
- **Wired into the Better Auth `hooks.before` for BOTH `/phone-number/send-otp` and `/phone-number/verify`** as the first action; it rewrites `ctx.body.phoneNumber` to the canonical value via the returned `{ context: { body } }`. Confirmed against the installed Better Auth (`dist/api/dispatch.mjs` deep-merges a before-hook's `context.body` into the endpoint context before the handler + after-hook run), so the resend cooldown, daily cap, `Verification.identifier`, Twilio delivery, verify lookup, and resulting `User` identity ALL key on the same canonical number. Invalid/non-Oman input is rejected **before** the cooldown/cap lookups, before any code is generated, and before Twilio is ever called (stable code `INVALID_PHONE_NUMBER`; the client maps it to a localized `auth.invalidPhoneNumber` message added to all 8 locales).
- **Existing-user compatibility:** repository/seed/test evidence (bootstrap-staging-admin `+968…`, all fixtures `+968…`, the onboarded `+96898115159`) shows the established identity convention is already canonical `+968` E.164, and the normalizer is a **no-op** for canonical input — so returning users are unaffected and NO identity migration is created here. Before the (separate, approved) deploy, a read-only DB audit of distinct `User.phoneNumber` formats should confirm zero non-canonical rows. Better Auth + Twilio architecture unchanged; no schema/migration. **VERIFIED BY TEST; NOT YET VERIFIED LIVE** (local commit only, not pushed/deployed).
**Alternative(s) considered:** Client-side normalization as the boundary (rejected — never authoritative; kept only as optional UX). Duplicating normalization in send/verify/cooldown/cap/lookup (rejected — the whole bypass came from divergent representations; one authority is the fix). Restricting the national number's leading digit to mobile prefixes 7/9 (deferred — the `+968` country restriction is the abuse control; over-restricting risks rejecting valid numbers). A one-time identity-canonicalization migration (not done — evidence says existing users are already canonical; a breaking migration without DB proof is out of this gate per its own rules).

### 2026-08-15 — P1 security gate: durable distributed OTP rate limiting (dedicated Postgres `AuthRateLimit` table)
**Context:** The audit's P1 — the in-memory limiter (`rate-limit/rate-limiter.ts`, booking/review only) is process-local, so on Vercel each warm instance keeps its own counter and cold starts reset it (effective ceiling `limit × instances`, not a global cap). The per-phone OTP controls (30s cooldown + daily cap) were already DB-backed/durable, but there was **no per-IP control** on the auth surface. Approved store: **Option 1 — a dedicated PostgreSQL table** (reuse the DB BARQ already depends on; explicitly NOT Redis/Upstash/KV and NOT the Better Auth `verifications` table).
**Decision:**
- New model **`AuthRateLimit`** (`auth_rate_limits`: `key` PK, `count`, `windowStart`, `expiresAt`, index on `expiresAt`) + an additive-only migration (`20260815120000_auth_rate_limit`) — **created, NOT applied to staging in this gate.** Stores ONLY a fixed-window counter — never a raw IP/phone/OTP/session/token/PII. Better Auth tables untouched.
- **Atomic** counter via a single `INSERT … ON CONFLICT DO UPDATE … RETURNING` (`durable-rate-limiter.ts`) evaluated against the DB clock — concurrent requests serialize on the row's write lock (same mechanism as the booking oversell guard), so there is no count-then-increment race and no separate `SELECT`. **Fail-closed** on any store error (deny + log without PII); since the store IS the primary Postgres the OTP flow already needs, a "store outage" is not an attacker-controllable bypass.
- **Trusted IP** (`rate-limit/client-ip.ts`): resolves the client IP from **Vercel's platform-set `x-real-ip` ONLY** (a single value the client cannot forge). **`x-forwarded-for` is deliberately NOT trusted** — its leftmost token is client-spoofable (Better Auth's own `getIPFromHeader` documents and refuses this), so trusting it would let an attacker rotate the value to evade the IP limiter. A missing/multi-valued `x-real-ip` → one shared `unknown` bucket (LIMITS, never bypasses). *(Pre-push review correction: an earlier draft fell back to the leftmost `x-forwarded-for`; that spoofable fallback was removed before the P1 commit was pushed.)*
- **No PII in the store:** BOTH identities are **HMAC-SHA256'd with the existing `BETTER_AUTH_SECRET`** (one shared primitive `hmacRateLimitKey`, no new secret) before becoming a key — the IP hash and the **HMAC of the canonical +968 phone**. `auth_rate_limits.key` therefore holds only opaque digests: **no raw IP and no raw phone**, never logged raw.
- **Scopes** (checked in the Better Auth `hooks.before`, after P0-1 canonicalization, before any code generation / Twilio): SEND → durable per-IP cap (default 15/h — the new cross-phone control) + durable per-phone cap keyed on the HMAC of the canonical +968 phone (default 6/h), **on top of** the preserved 30s cooldown + daily cap; VERIFY → durable per-IP cap (default 30/h). **No per-phone verify cap** — that would enable a victim-phone lockout DoS; per-code brute force stays capped by Better Auth's `allowedAttempts` (3). Keys are namespaced (`otp:send:ip:` / `otp:send:phone:` / `otp:verify:ip:`), no cross-limiter collision.
- **TTL:** lazy window reset inside the atomic UPSERT + opportunistic best-effort sweep of long-expired rows (5% of sends, fire-and-forget) — **no new cron**. **429 contract:** reuses `TOO_MANY_REQUESTS` with a generic message (no counter/key/IP/phone/store detail) — no web/iOS client change.
- Tunable via optional `AUTH_OTP_*` env vars (fail-fast on malformed). Better Auth + Twilio architecture unchanged; no external service, no new secret. **VERIFIED BY TEST; migration NOT applied to staging; live QA pending.**
**Alternative(s) considered:** Upstash/Vercel KV/Redis (rejected — new external service + secrets + cost; Postgres suffices, per the approved scope). Better Auth's built-in DB rate limiter (rejected — also needs its own table/migration, is IP-only, and is awkward to combine with the canonical-phone dimension). Reusing the `verifications` table for IP counters (rejected — overloads a Better-Auth-owned table whose shape is unverified). A per-phone verify limiter (rejected — victim-lockout DoS).
