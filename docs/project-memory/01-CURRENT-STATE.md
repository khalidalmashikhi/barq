# 01 — Current State (as-built inventory)

**Read this file first for any non-trivial task.** It captures what is actually real in the repository today, as distinct from what is planned (`03-PRODUCT-REQUIREMENTS.md`) or aspirational in the older architecture docs. Last inspected during the project-memory phase that created this file; re-verify against real files before relying on a claim here for anything security- or money-adjacent.

This file gives the capability-level summary; `15-DATA-DICTIONARY.md` gives the entity-level detail behind each row of the table below, `16-BUSINESS-RULES.md` gives the specific, ID'd rules (with honest enforcement status) that govern each capability, `18-DOMAIN-MODEL.md` gives the Bounded-Context grouping, and `21-ENGINE-SPECIFICATIONS.md` gives the per-engine Purpose/Responsibilities/Dependencies detail.

## Architecture

Single Next.js 15 (App Router) + React 19 + TypeScript application at the repo root — **not a monorepo** (no `turbo.json`/`pnpm-workspace.yaml`/`nx.json`). PostgreSQL via Prisma (37 models, `prisma/schema.prisma`), Better Auth for phone+OTP authentication, next-intl for 8-locale i18n, deployed on Vercel (`vercel-build` script runs `prisma migrate deploy && next build`; one cron job, `expire-stale-bookings`, every 30 minutes).

```
src/app/          Next.js routes ([locale]/ pages + api/ route handlers)
src/lib/          domain logic: booking/, provider/, admin/, contracts/, otp/, auth/, audit/,
                  observability/, notifications/, services/, dashboard/, i18n/
src/components/   UI components, grouped by feature area
src/i18n/         next-intl config — locales.ts, routing.ts, request.ts
prisma/           schema.prisma, migrations/, seed.ts
messages/         8 locale dirs × 10 JSON namespaces (static, developer-maintained)
scripts/          env-schema.ts + validate-env.ts (predev/prebuild gate, fails fast on bad config)
docs/             12 numbered subdirectories + docs/08-governance/adr/ (10 ADRs)
```

## Known drift between the architectural constitution and reality

- **ADR-0011 mandates versioned public APIs** (`/api/v1/...`). **(Corrected 2026-08-14):** the versioned surface now EXISTS — **public** (Gate 1: services/service-detail/availability/categories/providers), **authenticated customer** (Gate 2: `/me`, `/me/bookings*`, `/me/notifications*`; Gate 3: booking create/cancel + timeline + notification-read), and **authenticated provider READ** (Gate PB: `GET /api/v1/me/provider` state + `/profile` + `/services[/:id]` + `/availability` + `/bookings[/:id]` + `/verification`). All are thin JSON adapters over the existing `src/lib/**` domain readers (allow-list DTOs, shared locale/error/pagination helpers, money-as-string), reusing the same authoritative functions the web uses. **Provider notifications reuse the role-agnostic `/api/v1/me/notifications` feed (no separate provider feed exists — not duplicated).** **(Updated 2026-08-15, Gate PC:)** the **provider WRITE APIs (Gate PC)** now EXIST as thin `/api/v1` adapters — implemented **LOCALLY (commit `6520000` on `staging`), NOT yet pushed/deployed and VERIFIED BY TEST ONLY (not live-QA'd)**: `PATCH /me/provider/profile`; `POST /me/provider/services`, `PATCH /me/provider/services/{id}`, `POST /me/provider/services/{id}/publish`, `POST /me/provider/services/{id}/unpublish`; `POST /me/provider/availability`, `PATCH /me/provider/availability/{id}`, `DELETE /me/provider/availability/{id}`; `POST /me/provider/bookings/{id}/accept`, `.../reject`, `.../start`, `.../complete`. Each is a thin adapter over the existing Server Action (`createService`/`updateService`/`publishService`/`unpublishService`/`createAvailabilitySlot`/`updateAvailabilitySlot`/`deleteAvailabilitySlot`/`updateProviderProfile`/`acceptBooking`/`rejectBooking`/`startBooking`/`completeBooking`) — no new business logic. A pre-authenticating wrapper (`withApiV1ProviderMutation`) runs `requireProvider()` **before** the action so the action's browser `redirect("/")`-on-unauth path can never emit a 307 instead of a clean JSON 401; each action then applies its own stricter gate (`requireApprovedProvider`) internally. Ownership stays at the domain boundary (**no client `providerId`**; missing/not-owned → **uniform 404**, anti-enumeration); JSON bodies are adapted to the `FormData` the actions expect (absent = leave unchanged, `""` = clear); success re-reads via the same ownership-scoped GET reader and returns the existing DTO (**no raw Prisma objects**). Deferred within Gate PC (explicit): **standalone price mutation** (no provider price-edit domain exists — the initial ACTIVE price stays bundled in service creation; `update-service.ts` records price-edit as an un-made future decision), **verification-document upload (v1)**, **provider media mutations**, and **provider application/resubmission API**. **Provider payments/payouts: NOT STARTED.** Provider earnings-summary still deferred. The pre-`/api/v1` routes under `src/app/api/` (auth, provider media/documents, contracts, webhooks, cron) remain unversioned by design.
- **ADR-0009 (Better Auth user-model separation) is still "Draft v0.1 — Architecture Review pending"** in its own document header, even though the schema already implements the decision it describes (`AuthUser` model exists, `Session`/`Account` already target it).
- **Oman phone identity is canonicalized server-side (P0-1 security hardening, 2026-08-15).** `normalizeOmanPhone` (`src/lib/otp/normalize-oman-phone.ts`) is wired into the Better Auth `hooks.before` for `/phone-number/send-otp` and `/phone-number/verify`, rewriting the phone to one `+968XXXXXXXX` E.164 form so the resend cooldown, daily send cap, `Verification.identifier`, Twilio delivery, verify lookup, and `User` identity all key on it; non-Oman/malformed numbers are rejected **before** any SMS is sent. Closes the SMS-pumping / rate-limit-bypass / identity-fragmentation risk. Better Auth + Twilio architecture unchanged, no schema change. **DEPLOYED to staging** (commit `6f95889`; existing users verified 3/3 canonical, no migration needed).
- **Durable distributed auth/OTP rate limiting (P1 security hardening, 2026-08-15).** A dedicated PostgreSQL `AuthRateLimit` table (`auth_rate_limits`) backs cross-instance fixed-window limiters wired into the Better Auth `hooks.before`: per-IP + per-canonical-phone caps on send-OTP and a per-IP cap on verify-OTP, **on top of** the preserved 30s cooldown + daily cap. Atomic single-statement UPSERT (no race), fail-closed on store error. **Trusted IP = Vercel's `x-real-ip` ONLY** (`x-forwarded-for` is NOT trusted — leftmost is spoofable; missing → shared limited `unknown` bucket). **Both identities are HMAC'd** with `BETTER_AUTH_SECRET` (IP hash + HMAC of the canonical +968 phone), so `auth_rate_limits` stores **opaque keys only — no raw IP or raw phone**, never logged raw. TTL via lazy reset + opportunistic sweep (no cron), `TOO_MANY_REQUESTS`/429 (no client change). **No Redis/Upstash/KV, no new secret.** Replaces reliance on the process-local in-memory limiter (which stays for booking/review only). **Migration `20260815120000_auth_rate_limit` created but NOT YET APPLIED to staging; VERIFIED BY TEST, live QA pending.** See `12-DECISIONS.md`.
- `messages/ar/landing.json` uses the incorrect Arabic spelling **"بارق"** in 13 places; `messages/ar/common.json`'s `appName` correctly uses **"برق"**. See `13-OPEN-QUESTIONS.md`.
