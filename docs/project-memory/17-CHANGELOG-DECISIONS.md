# 17 — Changelog & Decisions Timeline

The permanent architectural and product decision timeline. Distinct from `12-DECISIONS.md`, which logs granular, tactical implementation decisions made *during* a specific phase of work (e.g., "reused enum X instead of creating a new one"); this file logs the higher-level decisions that shape the product and architecture across phases. Cross-link between the two where a tactical decision was made *in service of* one of these — don't duplicate the same fact in both files.

Entries marked **ADR-backed** correspond to a formally Approved (or, for ADR-0009, still-Draft) Architecture Decision Record under `docs/08-governance/adr/` — the ADR is the authoritative source; this timeline summarizes it. Entries marked **Product Direction — not yet an ADR** are real, stated product decisions captured in `docs/project-memory/` during this project's documentation phases, but have not gone through the formal ADR/RFC process (`docs/00-foundation/PROJECT_RULES.md`) — they are durable working direction, not yet a Locked architectural constitution entry. Do not conflate the two when citing authority for a decision.

### 2026-07-05 — Modular Monolith, not microservices
**Decision:** BARQ is one deployable application, internally divided into modules aligned to `DOMAIN_MODEL.md`'s Bounded Contexts; cross-module access only through explicit interfaces/domain events.
**Reason:** Avoids premature distributed-systems complexity while still keeping module boundaries real and enforced.
**Impact:** Every future engine (Category, Business, Financial, etc.) is a new module within the same app, not a new service. **ADR-backed: ADR-0002.**

### 2026-07-05 — Bilingual by design (Arabic + English co-equal)
**Decision:** Arabic and English are co-equal architecture, not "Arabic + a bolted-on translation layer." RTL designed-in, no hardcoded strings, language-neutral domain/API layer.
**Reason:** BARQ's core market is bilingual by nature; retrofitting bilingual support after building English-first was judged more expensive than designing for it from the start.
**Impact:** Every entity holding user-facing text (Provider, Service, Notification, etc.) uses a bilingual `{ar, en}` JSON shape from day one. **ADR-backed: ADR-0005** (language-count scope later superseded by ADR-0010; all other principles remain fully in force).

### 2026-07-05 — PostgreSQL + Prisma + UUID v7 database baseline
**Decision:** PostgreSQL as the primary database, Prisma as ORM, UUID v7 primary keys, all timestamps UTC, money as Decimal/Currency pairs (never Float), files in Object Storage with DB storing metadata only.
**Reason:** UUID v7 gives time-ordered, index-friendly, multi-region-ready IDs without the coordination cost of sequential integers across a future distributed setup.
**Impact:** Every model created since follows this convention without exception (verified — all 37 current models use `@id @default(uuid(7))`). **ADR-backed: ADR-0006.**

### 2026-07-05 — Next.js / TypeScript / Node.js / Vercel stack
**Decision:** Next.js + React + TypeScript frontend; Next.js Route Handlers + Server Actions on Node.js LTS backend; Vercel hosting (dev and initial production).
**Reason:** Single-framework simplicity for a small team, with Vercel's tight Next.js integration reducing deployment friction.
**Impact:** `vercel-build` script, `vercel.json` cron config, and the entire deployment pipeline (Phase 5.2) are built specifically against this choice. **ADR-backed: ADR-0007.** Vercel platform affinity is explicitly noted in the ADR as an accepted, non-permanent trade-off.

### 2026-07-05 — AI Agent Boundaries: 17 permanent rules
**Decision:** An AI agent may never bypass authorization, access the database directly outside its granted API, modify financial records or execute payouts, or approve providers/finalize contracts autonomously — every such action requires mandatory human approval and is universally auditable.
**Reason:** BARQ handles real money and real trust decisions (provider verification); autonomous AI action in these areas is an unacceptable risk regardless of how capable the AI becomes.
**Impact:** Binding on any future AI Center work (planned engine #14, roadmap Phase 8) — see `11-SECURITY-POLICY.md` and BR-020. **ADR-backed: ADR-0008.**

### 2026-07-07 — Better Auth gets its own AuthUser model, separate from domain User
**Decision:** Better Auth's infrastructure-owned fields (name, email, emailVerified, phone) live on a new `AuthUser` model; BARQ's domain `User` stays UUID-v7-only with no name/email fields, linked via a nullable unique field.
**Reason:** Keeps Better Auth's library-specific requirements from leaking into and constraining the domain model.
**Impact:** `Session`/`Account` FKs target `AuthUser`, not `User`. **ADR-backed: ADR-0009 — still Draft v0.1, Architecture Review pending**, even though the schema already implements it. See `13-OPEN-QUESTIONS.md`.

### 2026-07-11 — Multilingual expansion to 8 officially targeted languages
**Decision:** Arabic, English, German, Italian, Polish, French, Czech, Russian — expanding from ADR-0005's original 2-language scope.
**Reason:** Broader tourist origin coverage for Oman's international visitor base.
**Impact:** `messages/` directory structure, `src/i18n/locales.ts`, and `src/middleware.ts`'s locale matcher all reflect exactly these 8 locales. **ADR-backed: ADR-0010** (supersedes ADR-0005's language-count scope only — all of ADR-0005's other principles remain in force).

### 2026-07-11 — API-First & Mobile-Ready Architecture
**Decision:** Reusable capabilities exposed via stable, versioned APIs (not Server-Action-only); one shared business-logic layer serves Web, a future mobile app, AI agents, and future partners alike; domain layer independent of React/Next.js.
**Reason:** Avoids duplicating business logic across a future mobile app or partner integration; keeps the option open to add a React Native/Expo client without a rewrite.
**Impact:** Every future engine's capabilities should be designed API-first from the start. **Known current drift**: no `/api/v1/` versioning exists on any endpoint today — see BR-018. **ADR-backed: ADR-0011.**

### 2026-07-22 — Product direction: full product requirements, 15 planned platform engines
**Decision:** BARQ's product direction expands to include: data-driven categories/subcategories with configurable visibility (`PUBLIC`/`HIDDEN`/`LINK_ONLY`/`INVITE_ONLY`/`SCHEDULED`/`ARCHIVED`); individual-vs-commercial provider onboarding with category-specific requirements; a full financial model distinguishing gross/discount/tax/commission/net/paid/outstanding/settlement/transfer; flexible commission models (percentage/fixed/hybrid/zero/manual); flexible pricing control (admin/provider/both-with-approval/RFQ); and 15 named platform engines to realize all of this.
**Reason:** Stated as the long-range product vision to guide incremental engine-by-engine implementation, one scoped phase at a time.
**Impact:** Captured in full in `03-PRODUCT-REQUIREMENTS.md`; broken into a phased roadmap in `../plans/ROADMAP.md`. **Product Direction — not yet an ADR.** Should be formalized into one or more ADRs once the first engine (Dynamic Category Management) reaches implementation, per `docs/00-foundation/PROJECT_RULES.md`'s ADR/RFC process.

### 2026-07-22 — Communication stays inside BARQ; provider contact information is hidden from tourists
**Decision:** Provider direct phone/WhatsApp/email must never be exposed to tourists; all customer-provider communication (messaging, support tickets, booking inquiries, quote requests) must be mediated by BARQ.
**Reason:** Trust, safety, and platform-stickiness (disintermediation prevention) for a marketplace business model.
**Impact:** Already true today by omission (no contact-exposing feature exists yet) — becomes an actively enforced design constraint for the future Internal Messaging Center and Support Center. See `10-COMMUNICATION-POLICY.md`, BR-002/BR-003. **Product Direction — not yet an ADR.**

### 2026-07-22 — Security remains code-controlled; business configuration becomes admin-controlled where safe
**Decision:** Core security, authentication, payment integrity, and permission enforcement must remain code-controlled. Business configuration (categories, pricing, commissions, translations, homepage content) may become admin-controlled where doing so is safe.
**Reason:** Balances the product goal of a fully configurable, no-deploy-needed business platform against the non-negotiable need for security/financial integrity to never be misconfigurable by non-engineering staff.
**Impact:** The governing dividing line for every future engine's design — see `11-SECURITY-POLICY.md`, BR-006. **Product Direction — not yet an ADR**, though it is consistent with and extends ADR-0008's existing human-in-the-loop principle for AI specifically.

### 2026-07-23 — BR-001 (provider-approval enforcement) closed from Target to Enforced
**Decision:** A provider whose `status` is not `APPROVED` (i.e. `APPLIED`, `UNDER_REVIEW`, `REJECTED`, or `SUSPENDED`) is now blocked in code from creating, editing, publishing, unpublishing, archiving, or duplicating a service, and from creating, editing, deleting, or bulk-creating availability slots.
**Reason:** `16-BUSINESS-RULES.md` had documented this as a real, verified gap since the initial Project Memory Enhancement pass — `requireProvider()` only confirmed a `Provider` row existed, never that it had been approved. Phase 0 (Foundation Hardening) closed the gap via `requireApprovedProvider()`, a narrow composition over `requireProvider()` (`ARCHITECTURE_PRINCIPLES.md` Principle 18 — composition over duplication), scoped to exactly the 8 service/availability-management call sites BR-001 named.
**Impact:** `src/lib/auth/rbac.ts` gains `requireApprovedProvider()`; `src/lib/auth/errors.ts`'s `ForbiddenError` gains an optional `code` field to distinguish `PROVIDER_NOT_APPROVED` from a missing provider profile; 8 provider action files updated; translations added in all 8 locales; 9 test files / 34 tests cover the new behavior (3 of those test files — `create-service`, `update-service`, `duplicate-service` — were written in Phase 0.1, closing a gap where the action files existed but had no test coverage at all). Booking-lifecycle actions (accept/reject/start/complete) and read-only provider queries were deliberately left ungated — out of BR-001's named scope, and moot in practice since an unapproved provider cannot have a `PUBLISHED` service to receive bookings against. **Product Direction — not yet an ADR** (an RBAC composition of this size was judged not to require one; see `ARCHITECTURE_PRINCIPLES.md` for the general principle it follows).

### 2026-08-09 — Provider Review / Reject / Resubmit lifecycle (REJECTED state)
**Decision:** `ProviderStatus` gains a real `REJECTED` value. An admin may reject a pending application (`APPLIED`/`UNDER_REVIEW`) with a **mandatory** reason (`rejectProvider()`); the current reason is stored on new nullable `Provider.rejectionReason`/`rejectedAt`/`rejectedByAdminId` (mirroring the `approvedBy*` design) and permanently in the `provider.rejected` audit payload. A rejected applicant self-serves `resubmitProviderApplication()` (`REJECTED → APPLIED`, own identity only), which clears the current rejection fields (audit history retained) and re-enters the existing review queue. `UNDER_REVIEW` is deliberately kept as a valid enum value and an approvable/rejectable input, but nothing transitions *into* it (no Start Review). No maximum resubmission count.
**Reason:** Closes the long-documented reject/resubmit gap (BR-001's related note, `19-EVENT-CATALOG.md`'s `ProviderRejected`, `20-PERMISSION-MATRIX.md`'s target Reject permission) with the smallest correct model for BARQ's current scale — deferring review assignment, multi-reviewer workflow, KYC/document verification, and appeal workflow.
**Impact:** Additive migration only (`REJECTED` enum value + 3 nullable columns + `ProviderRejectedBy` relation + `rejectedByAdminId` index) — no backfill, existing rows unaffected. Access: `REJECTED` behaves like `APPLIED` — `requireProvider` admits it (edit profile/media, own preview), `requireApprovedProvider` still blocks service/availability/booking management; public storefront stays `APPROVED + visible`; `visible` untouched by reject/resubmit; customer access intact (no RBAC code change). New `PROVIDER_REJECTED` in-app Notification Center notification (static, all 8 locales, reason NOT embedded, no external email/SMS); `provider.rejected` / `provider.resubmitted` audit events. Both mutations use an optimistic conditional-update guard against concurrent/stale transitions. Two new mutations + admin Reject UX (reason input) + rejected-reason display + applicant rejected/resubmit UX + status maps/filters threaded + i18n ×8 + focused tests. **Product Direction — not yet an ADR** (a lifecycle addition following existing patterns; no new architectural principle introduced).

### 2026-08-10 — Provider Verification & Documents (Gate 1: schema + domain contract)
**Decision:** Provider verification documents use a **hybrid registry** architecture. A new `ProviderDocument` model stores document metadata; its `type` is a **registry-validated String** (`src/lib/provider-document-types`, mirroring `Category.serviceTypeKey` / `FeatureFlag.key`) — **NOT** a Prisma enum, **NOT** a DB catalog, and **without** a DB CHECK, so adding a document type is a pure code change (registry entry + i18n label) with **zero migration**. Only the fixed 3-state review lifecycle is a Prisma enum: `ProviderDocumentStatus { PENDING, APPROVED, REJECTED }`. Requirement rules are **code-controlled** (`requiredDocumentTypesFor`, compliance-adjacent → off the admin-editable side per `11-SECURITY-POLICY.md`), keyed **only** by the stable `ProviderType` axis (INDIVIDUAL → identity evidence; COMPANY → commercial registration; `TOURISM_LICENCE` is recognized but not a universal blocker). The public `Category` taxonomy is deliberately **never** consulted for compliance (BR-024: browse/SEO only); the resolver takes a provider-context shape so future activity-specific rules can be added without a schema change. Documents are **private** artifacts — the DB stores only the private-bucket `objectKey`, never a public/permanent/signed URL. Gate 1 keys: `IDENTITY_PROOF`, `COMMERCIAL_REGISTRATION`, `TOURISM_LICENCE` (product-level evidence categories, **not** asserted Omani legal requirements).
**Reason:** Reuses BARQ's established "governed-extensible string key + code registry" convention to avoid enum-migration churn and a premature admin-managed compliance catalog, while cleanly promotable to a DB catalog later (registry → catalog, `type` unchanged) if needed. Supersedes the audit's earlier `ProviderDocumentType` Prisma-enum sketch.
**Impact:** Additive migration only (`ProviderDocumentStatus` enum + `provider_documents` table + Provider FK CASCADE + reviewer FK SET NULL + indexes) — no backfill, no `ProviderStatus` change, no mutation of existing rows. **Existing APPROVED providers are grandfathered:** no approval gate is wired into `approveProvider` in Gate 1, so no provider is retroactively required to submit documents, suspended, or hidden; the Verified badge (still `status === "APPROVED"`) is unchanged. A pure completeness primitive (`resolveRequiredDocumentBlockers`) is defined for the future `assertProviderApprovable()` but not enforced. Upload/review/private-storage/signed-URL/UI/notifications remain later, separately-approved gates (with an ops dependency to provision a private bucket). **Product Direction — not yet an ADR** (follows the existing ADR-0015 registry convention; no new architectural principle introduced).

### 2026-08-10 — Provider Verification & Documents (Gate 2: private storage + mutation/review domain)
**Decision:** Verification documents live in a **separate PRIVATE Supabase bucket** (`SUPABASE_DOCS_BUCKET`, no default, **no public fallback**, fail-closed) — distinct from the public media bucket. New private storage primitives (`uploadPrivateObject` with `upsert:false`, `removePrivateObject`, `createSignedObjectUrl` with an attachment `downloadFilename`, `isDocumentStorageConfigured`) sit alongside the untouched public-media functions. Upload validation is **magic-byte** (content signature), not just declared MIME, capped at **`MAX_DOCUMENT_BYTES = 4 MB`** (Option 1 MVP, chosen after verifying Vercel's non-raisable **4.5 MB** Function request-body ceiling). Concurrency uses an **opaque `versionToken = sha256(objectKey)`** (never the raw `objectKey`): every mutation re-loads the doc, verifies the token, then does an atomic conditional `updateMany`/`deleteMany` bound to `objectKey`(+`status`); mismatch/0-rows → `STALE_DOCUMENT` (RC3 contract). The view path authorizes owner-provider **or** admin, mints a **60-second** signed URL, 302-redirects with `Cache-Control: no-store`, and returns a **uniform 404** for missing/not-owned/not-configured (never reveals existence). Audit events (`provider.document_uploaded/replaced/deleted/approved/rejected`) carry metadata only — never bytes, `objectKey`, or signed URLs.
**Reason:** Documents are sensitive KYC-adjacent artifacts; a private, fail-closed bucket + short-lived signed URLs + opaque tokens prevent enumeration, stale-overwrite races, and accidental public exposure, while reusing the existing storage/audit conventions.
**Impact:** Additive domain + transport only; no schema change beyond Gate 1. Committed locally (`141a445`), **not pushed**; the private bucket is **not** provisioned (inert on staging).

### 2026-08-10 — Provider Verification & Documents (Gate 3: approval gate + provider/admin UX + badge fix)
**Decision:** Wire the Gate 1/2 foundation into the product. (1) **Server-authoritative approval gate:** `approveProvider` composes `assertProviderApprovable` (built only from the existing `requiredDocumentTypesFor` + `getProviderDocumentSnapshots` + `resolveRequiredDocumentBlockers` primitives — no second completeness engine) and refuses with `INCOMPLETE_DOCUMENTS` + ordered blockers, performing no transition/audit/notify when a required doc is missing or not `APPROVED` (**BR-029**). (2) **Provider surface:** a new `/[locale]/provider/verification` page (documents only, gated by the existing `requireProvider`), a dashboard readiness card, and application-page links — all reading one shared server-derived summary (`getProviderVerificationData`), no checklist logic duplicated in React. (3) **Admin surface:** a Verification Documents section on the existing provider detail page (view/approve/reject-with-mandatory-reason, opaque `versionToken`, `STALE_DOCUMENT` → "reload" message) plus a proactive blocker panel and a disabled Approve when blocked. (4) **Notification:** `PROVIDER_DOCUMENT_REJECTED` added to the existing helper — static, 8-locale, created only on a successful admin doc-reject, **never** embeds the admin's free-text reason (shown on the verification page), post-commit fire-and-forget (failure never rolls back the review). (5) **Verified-badge defect fixed:** `ProviderProfileView` now gates the badge on `status === "APPROVED"`, so provider/admin previews of non-approved providers no longer show a false "Verified" signal (no new field/status). Mutation transport for upload/replace/delete/review converted to progressive `<form>` route handlers (>1 MB multipart can't be server actions) with 303 redirects carrying `?docNotice`/`?docError`.
**Reason:** Makes "Verified Provider" mean an admin actually reviewed the required evidence, without touching auth/RBAC/ProviderStatus/schema; the gate is enforced in code (disabled buttons are not sufficient) yet degrades gracefully and preserves grandfathering.
**Impact:** Additive UI + i18n (8 locales × provider/admin) + tests only; **no** schema/migration/`ProviderStatus`/auth/permission/payment/public-API change (verified by protected-path scan). Existing APPROVED providers untouched; replacing an approved doc → `PENDING` while the provider stays operational; doc-level rejection ≠ provider-level rejection. **Not committed** (Gate 3); Gates 1–3 remain **local-only, unpushed**; the Gate-1 migration is **not applied** and the private bucket is **not provisioned** — the documented launch-blocking runtime dependency.

### 2026-08-11 — Social Login (Gates 1–3: Google, on the identity bridge)
**Decision:** Add Google social sign-in (Apple deferred) as an ADDITIONAL method — phone + OTP (Twilio) remains fully supported. **Identity is anchored on the BARQ `User`, keyed on `authUserId`, never on email/name.** Gate 1 (schema): `User.phoneNumber` made nullable (kept `@unique`; PostgreSQL NULLs are distinct → many phone-less users allowed) + `AuthUser.image` added (Better Auth 1.6.23's default social mapping writes `image: profile.picture`). Gate 2 (bridge): `resolveBarqUser()` is a deterministic, race-safe state machine — already-linked → same User; verified phone matching an UNLINKED legacy User → atomic claim (preserves Customer/Provider/Admin/Staff/relations); social AuthUser with no phone → `User(phoneNumber=null)`+Customer; brand-new verified phone → User+Customer. An UNVERIFIED phone never claims. `reconcileVerifiedPhone()` completes an UNUSED verified phone onto the same User, or returns `PHONE_ALREADY_LINKED_TO_ANOTHER_ACCOUNT` (**no silent merge, nothing moved/deleted**). Gate 3 (Google): `socialProviders.google` fail-closed (only when `GOOGLE_CLIENT_ID`+`GOOGLE_CLIENT_SECRET` both set; secret server-only); `account.accountLinking` = `{ enabled:true, trustedProviders:[], allowDifferentEmails:false, updateUserInfoOnLink:false }` — **no email-based auto-merge** (BARQ phone users hold synthetic unverified `@phone.barq.internal` emails, so OTP↔Google is never auto-linked); explicit `linkSocial()` from Settings is the intended existing-user path; `signIn.social` from `/login` with FIXED internal callback URLs (no open redirect). Disconnect deliberately NOT offered in MVP (can never lock a user out). **A phone-less Google customer is valid** (`User.phoneNumber = null`); phone verification is required later (booking / become-provider) — deferred to the phone-gating gate.
**Reason:** Lower-friction signup for tourists (Google/Apple) without weakening BARQ's phone-centric identity or risking duplicate/merged Provider/Admin identities. Better Auth's email-based linking is neutralized by BARQ's synthetic-email reality, so matching email/name never transfers privileges.
**Impact:** Gate-1 additive migration (`20260811090000_social_login_phoneless_user`) — **unapplied, unpushed**. Gates 1/2/3 are three separate local commits. No RBAC/ProviderStatus/booking/payment/pricing change; no Better Auth Account-schema change (existing Account table stores OAuth accounts). Google Cloud credentials + Vercel env are NOT provisioned yet.

### 2026-09-11 — Provider Verticals: verified, approval-gated activity authorization (Phase 3B Phase 1)
**Decision:** A regulated listing (a guided TOUR, a VEHICLE_RENTAL) may be published only by a provider holding the matching **approved AND compliant** `ProviderVertical` — a first-class, reviewed *activity capability* kept strictly separate from `Provider.providerType` (INDIVIDUAL/COMPANY business form) and from `ProviderCategory` grants (taxonomy only, never authority). New enums `ProviderVerticalType {TOURIST_GUIDE, RENTAL_COMPANY}` / `ProviderVerticalStatus {PENDING_REVIEW, CHANGES_REQUESTED, APPROVED, REJECTED, SUSPENDED}` / `ProviderVerticalOrigin {PROVIDER_REQUEST, LEGACY_BACKFILL}`, a `ProviderVertical` model, a nullable `Service.offeringKind {TOUR, VEHICLE_RENTAL}` discriminator, and `Service.legacyVerticalExempt` (bounded, server-only grandfathering) — all additive in migration 53 (`20260910120000_provider_verticals`). `offeringKind` is derived **server-side** from the governed taxonomy (RENTAL serviceType → VEHICLE_RENTAL; the verified tourist-guide category → TOUR; never all EXPERIENCE), so a new regulated listing can never stay null-kind to bypass authorization. Draft creation is allowed while the vertical is requested (PENDING/CHANGES) but **publishing requires BOTH the Provider = APPROVED and the vertical = APPROVED + compliant**. Compliance reuses the ADR-0017 requirement engine on new vertical audiences: an **empty required policy fails closed** (`VERTICAL_POLICY_NOT_CONFIGURED`), and required documents whose requirement declares `evidenceExpires` must be APPROVED and unexpired (`ProviderDocument.expiresAt`, admin-confirmed at approval). Admin approval re-checks compliance **inside the transaction** (TOCTOU-safe). Suspension hides that vertical's published listings and freezes new bookings/publishing for it; **confirmed bookings are never auto-cancelled/refunded** and an APPROVED row is never silently churned on expiry. Legacy grandfathering never bypasses suspension. Minimum vertical requirements (`RENTAL_ACTIVITY_LICENCE`, `RENTAL_BUSINESS_REGISTRATION`, `TOURIST_GUIDE_LICENCE`) are seeded by an idempotent, staging-guarded bootstrap; the general INDIVIDUAL/COMPANY requirements are untouched.
**Reason:** BARQ's two regulated verticals have distinct legal/eligibility gates that a flat category grant cannot express; authorization must be server-authoritative, fail-closed, and independently reviewable per activity.
**Impact:** **DEPLOYED TO STAGING at commit `6f83b2d` (2026-09-11).** Migrations 53 (`20260910120000_provider_verticals`) and 54 (`20260911120000_seed_vertical_verification_requirements`, the idempotent baseline-policy seed) were applied to the staging database by `vercel-build`'s `prisma migrate deploy`, and the code is live on `barq-staging`; both vertical policies (RENTAL_COMPANY + TOURIST_GUIDE) are seeded and active. **Production (`barq`) remains UNTOUCHED and the legacy vertical backfill has NOT been run.** Runtime enforcement is therefore active on staging (unseeded verticals would fail closed; here they are seeded). **Product Direction — not yet an ADR.** See `15-DATA-DICTIONARY.md`/`16-BUSINESS-RULES.md` when this is promoted; ADR-0017 is the requirement-engine authority reused here.

### 2026-09-14 — Phase 3C Slice A deployed + Slice B: Vehicle Capacity Foundation (registered seats vs bookable capacity)
**Decision (context):** Phase 3C Slice A (customer-shell polish — shared bottom nav + always-visible language switcher; presentation-only, no schema) is **DEPLOYED to staging at commit `1f337654`** (migration count unchanged at 54; production untouched). Slice B then establishes the capacity data model that later daily-pricing/fare-calendar work depends on.
**Slice B decision:** Distinguish two DISTINCT vehicle capacity concepts. (1) **`Vehicle.bookablePassengerCapacity`** — the maximum number of CUSTOMERS who may book the vehicle (excludes the driver + operating guide). This is the RENAME of the existing `passengerCapacity` Prisma/client field; the PHYSICAL column is preserved unchanged via `@map("passengerCapacity")`, so all existing capacity data is untouched. (2) **`Vehicle.registeredSeats`** — a NEW nullable column: the official/registered total seat count (informational). Bookable capacity is **provider-entered**, never auto-derived by subtracting operator seats. Server-authoritative validation (`vehicle-input.ts`): both are positive integers within the existing platform ceiling (100), and `bookablePassengerCapacity <= registeredSeats` whenever registered seats are KNOWN (null registered → bookable stands alone); impossible pairs are rejected (`INVALID_INPUT`), never clamped. Capacity is **safety data, never a billing quantity** — the pricing engine bills a vehicle-style (FIXED: PER_VEHICLE/PER_BOOKING/PER_TRIP) price exactly once regardless of passenger count (locked by test). **Verification safety:** a provider edit that CHANGES a capacity field on a trusted/under-review vehicle (`verificationStatus` APPROVED or SUBMITTED) re-opens verification by resetting it to DRAFT (guarded `updateMany`, clears review metadata, dedicated audit event) so an unverified claim never masquerades as admin-verified — reusing the EXISTING asset-verification lifecycle, never touching the operational `Asset.status` axis, never auto-approving. Admin review surfaces both values distinctly. External contracts are deliberately preserved under the name `passengerCapacity`: the API v1 wire DTO/input (iOS-stable, `registeredSeats` added additively), the stored `Booking.vehicleSnapshot` JSON (historical bookings never reinterpreted), and audit payload keys.
**Fare-calendar requirement (locked, NOT built):** the future booking calendar must show the real authoritative **per-vehicle daily price inside every available date cell** (fare-calendar style; per Oman calendar day, never per passenger/hour; date-specific override wins; server-revalidated; no partial booking on drift). **Database uniqueness invariant (the safety arbiter):** a raw **PARTIAL UNIQUE INDEX** `rental_vehicle_day_reservations_active_vehicle_date_key ON (vehicleId, serviceDate) WHERE status IN ('HELD','CONFIRMED')` (Prisma 5.22 cannot express a partial unique in the DSL — same convention as `bookings_active_slot_per_customer_key`). This index — **not** any application pre-check, JS lock, count query, or process mutex — is the SOLE race arbiter: concurrent acquisitions of the same vehicle/day contend on it, exactly one `INSERT` commits, and the loser's whole transaction rolls back. RELEASED/EXPIRED/CANCELLED are EXEMPT, so historical rows stay for audit and never block re-acquisition of a freed day. Matches the repo convention (default **READ COMMITTED** `$transaction` + DB arbiter; **no** `isolationLevel: Serializable`, no retry loop — none exists anywhere in the codebase).

Historical rows are never deleted to free inventory.
**Hold TTL:** server-owned `RENTAL_HOLD_TTL_MINUTES = 10`; `expiresAt = now + TTL`. **Client input never sets expiry.**
**Idempotency contract:** group-level `idempotencyKey` + a SHA-256 `requestFingerprint` over the normalized request (offering + sorted unique days + passenger count; expected quote is drift-detection only, NOT identity; customerId is the lookup scope). Same key + same fingerprint → **replay** the same active group (no new rows, no expiry extension); same key + materially different request → **`IDEMPOTENCY_MISMATCH`**; concurrent identical requests converge on the winning group (the loser of the DB `(vehicle, day)` conflict re-reads by `(customerId, idempotencyKey)` and replays instead of surfacing a conflict). The `holdToken` is NEVER authorization — every release re-checks the authenticated owner.
**Atomic multi-date algorithm (`acquireDailyRentalHold(prisma, params)`):** validate (positive-integer passengers; non-empty, unique, well-formed, non-past, `<= MAX_RENTAL_HOLD_DATES = 62` days; canonicalize + sort); idempotency fast-path replay/mismatch; then ONE `$transaction`: re-read owner + public-gated owned offering + provider-global vertical compliance (`assertRentalVerticalCompliant`) + candidate-local vehicle readiness (`assertRentalVehicleReady`) + effective capacity (`checkCapacityOverride`; passenger count validated against it, **never** a price factor) + each selected `RentalOfferingDay` (each MUST be explicit `OPEN`; price = valid override else base; malformed → fail closed); authoritative total via the shared C2a `calculateVehicleDailyTotal` (`Prisma.Decimal`, 2dp, single currency); recompute the quote and, if the client supplied an expected total/currency or fingerprint that differs, return **`PRICE_CHANGED`** with the fresh quote and **write nothing**; expire stale targeted HELD rows; `createMany` all N day rows — a unique-index conflict on ANY date aborts the whole `INSERT` → the tx rolls back (**no partial hold, no partial price snapshot, no success audit**), mapped OUTSIDE to **`VEHICLE_DATE_CONFLICT`** (raw Prisma/PG never leaks); success `AuditLog` (`rental.daily_hold_acquired`) INSIDE the tx (its failure rolls the hold back). Non-consecutive dates reserve only the exact selected days; gaps are neither charged nor reserved.
**Conflict reader + C2c integration:** `getDailyRentalVehicleConflicts(vehicleIds, window, db, now?)` — read-only, bounded, one query, no N+1; returns `${vehicleId}|${dateKey}` keys for CONFIRMED rows and **unexpired** HELD rows only (expired-HELD/RELEASED/EXPIRED/CANCELLED ignored); a physical vehicle/day is binary (seats are never remaining inventory). The C2c resolver now consults it ONCE per page (batched over the page's ready vehicles + window): an `OPEN` configured day with an active conflict becomes `available: false, unavailableReason: "VEHICLE_CONFLICT"`, dailyPrice null, **dayState stays `OPEN`** (configured state kept separate from reservation state), and is excluded from the service-wide lowest rate. **`availabilityBasis` changed `"CONFIGURED"` → `"CONFIGURED_AND_RESERVATION_CHECKED"`.** It exposes NO customer id, booking id, hold token, expiry, or reservation metadata; stays READ-ONLY + `no-store`; adds no UI. **Not "guaranteed":** final acquisition still revalidates atomically (a conflict may arise between the read and the hold).
**Release + expiry primitives:** `releaseDailyRentalHold(prisma, {holdGroupId, customerId})` — only the owner (customerId where-predicate; foreign/missing → uniform `NOT_FOUND`), only `HELD → RELEASED`, idempotent (repeat → `releasedCount: 0`, no audit spam), in-tx audit, never touches CONFIRMED. `expireStaleDailyRentalHolds` (bounded general sweep, two-step select-ids-then-guarded-updateMany, only stale HELD → EXPIRED, never CONFIRMED) + `expireStaleHoldsForVehicleDates` (targeted, used inside acquisition — shared expiry rule). **No cron/scheduler introduced** (none established for this domain).
**Confirmation DEFERRED to C3/E2:** safe `HELD → CONFIRMED` requires a real Booking reference created in the later Booking-creation transaction (out of this slice's scope), so **no confirm function is implemented** (a partial/misleading confirmation was deliberately avoided). `CONFIRMED` exists as a valid state + additive nullable `bookingId` FK is in place; C3/E2 will transition every row of a hold group atomically against its Booking.
