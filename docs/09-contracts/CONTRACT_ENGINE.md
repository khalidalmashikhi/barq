# BARQ Electronic Contract Foundation

- **Purpose:** Documents the reusable Contract Engine built in Phase E.2 — a dedicated, booking-scoped contract domain object with its own lifecycle, template rendering, PDF generation, versioning, and history, plus the interfaces a future phase attaches electronic signature, QR verification, and approval workflows to.
- **Scope:** Contract domain model, lifecycle/transitions, contract numbering, template engine, PDF architecture, versioning/archive, history, and future extension points.
- **Out of Scope:** Electronic signature, QR verification, and government/employer/customer approval implementations (interfaces only — requirement #10); automatic contract generation on booking acceptance (prepared, not wired — §6); real branding/styled PDF output (§5); final legal contract wording (the template text is placeholder boilerplate, not reviewed legal copy).
- **Owner:** Whoever builds the next Business Feature that touches contracts (signature, approval, renewal) — keep current as the engine grows.
- **Status:** Added Phase E.2 (Electronic Contract Foundation).

```
│   ├── transition-contract.ts     transitionContract() — the single engine every status change passes through
│   └── index.ts
├── contract-number.ts           Human-readable, sequential, unique numbering (§4)
├── templates/                   Contract Template Engine (§5)
│   ├── template.ts                 ContractTemplate interface, bilingual content types
│   ├── service-templates.ts        Standard Service / Premium Service / Corporate
│   └── get-contract-template.ts    Factory by key (GOVERNMENT reserved, not implemented)
├── pdf/                          PDF Architecture (§7)
│   ├── pdf-generator.ts            ContractPdfGenerator interface
│   ├── simple-pdf-writer.ts        Minimal, valid, hand-rolled PDF byte writer (no new dependency)

├── create-contract.ts           createContractFromBooking() — the prepared Booking Integration point (§6)
├── generate-contract.ts         generateContractContent() — DRAFT -> GENERATED, renders + stamps generatedBy
├── record-contract-downloaded.ts DOWNLOADED event recorder (not a status transition)
├── create-contract-version.ts   Versioning & Archive (§8)

├── extensions/

```

This engine is a **library**, not yet a user-facing feature — no new API route or UI was built this phase (matching Phase E.1's own discipline of building the engine before the surface area that uses it). Every function above is directly callable and fully tested; a future phase wires them into Server Actions, API routes, and the Provider/Customer Dashboards.

## 2. Domain Model

**`BookingContract`** — one row per contract *version* (see §8), deliberately its own dedicated model (requirement #1: "Do NOT overload Booking"). It is **not** the pre-existing `Contract`/`ContractStatus` model already in `schema.prisma` — that model is a customer/provider platform-agreement concept (no `bookingId` at all), confirmed unused by any app code before this phase, and left completely untouched. `BookingContract` is named distinctly so the two are never confused.

| Field | Purpose |
|---|---|
| `bookingId` | The Booking this contract is for. |
| `contractNumber` | Unique, human-readable (§4). |
| `status` | `BookingContractStatus` (§3). |
| `templateKey` / `templateVersion` | Which template, and which version of its wording, generated `content` (§5). |
| `content` | Bilingual JSON contract body. Null until `GENERATED`. Immutable once set (§8). |
| `version` / `supersedesContractId` | This contract's own revision number and, if any, the row it replaces (§8). |
| `archivedAt` | Set when superseded by a newer revision — the contract is frozen from this point on. |
| `generatedByActorType` / `generatedByActorId` / `generatedAt` | Requirement #5's "Version, Created Date, Generated By." |

**`BookingContractEvent`** — an append-only history log (requirement #9/history), one row per meaningful event (`CREATED`, `GENERATED`, `ISSUED`, `ACTIVATED`, `DOWNLOADED`, `ARCHIVED`, `CANCELLED`, `COMPLETED`, `EXPIRED`, `SIGNED`). Deliberately **not** the same from/to-status-pair shape as Phase E.1's `BookingStatusEvent` — `DOWNLOADED` can happen many times with no status change at all, so this is a plain event log, not a transition log. `SIGNED` exists only so the future signature feature has somewhere to log to without another migration; nothing writes it yet.

Both models reuse Phase E.1's `BookingActorType` enum (`CUSTOMER`/`PROVIDER`/`SYSTEM`/`ADMIN`) rather than defining a parallel one.

## 3. Lifecycle Diagram

```
DRAFT ──► GENERATED ──► ISSUED ──► ACTIVE ──► COMPLETED
  │            │            │          │
  └────────────┴──► CANCELLED ◄─────────┘
                                         └──► EXPIRED
```

| From \ To | DRAFT | GENERATED | ISSUED | ACTIVE | COMPLETED | CANCELLED | EXPIRED |
|---|---|---|---|---|---|---|---|
| DRAFT | — | ✅ | ❌ | ❌ | ❌ | ✅ | ❌ |
| GENERATED | ❌ | — | ✅ | ❌ | ❌ | ✅ | ❌ |
| ISSUED | ❌ | ❌ | — | ✅ | ❌ | ✅ | ❌ |
| ACTIVE | ❌ | ❌ | ❌ | — | ✅ | ✅ | ✅ |
| COMPLETED / CANCELLED / EXPIRED | ❌ | ❌ | ❌ | ❌ | — | — | — |

`CANCELLED` is reachable from every non-terminal status (a contract can be called off at any stage); `EXPIRED` only from `ACTIVE` (a time-based lapse of an already-active contract). All three are fully terminal — **no speculative resurrection edge** (e.g. an `EXPIRED -> ACTIVE` "renewal") was added without a real renewal feature designing its own rule. This mirrors a real lesson from Phase E.1: an early draft of that engine's matrix added a speculative edge that turned out to cause a silent behavior regression once another function started depending on the matrix. This phase's matrix was designed narrowly from the start for the same reason.

Every transition goes through `transitionContract()` — the single engine, exactly mirroring Phase E.1's `transitionBooking()`. It additionally guards against writing to an already-archived contract (`ArchivedBookingContractError`), a concept Bookings have no equivalent of.

## 4. Contract Number

Format: `<prefix>-<year>-<6-digit sequence>`, e.g. `BARQ-2026-000123`. Backed by a Postgres sequence (`booking_contract_number_seq`, created via raw SQL in this phase's migration — Prisma's schema DSL only supports `autoincrement()` on an Int primary key, not a custom-formatted string). A sequence is the standard, concurrency-safe primitive for "no duplicates" — guaranteed by the database, not application discipline. `prefix` is configurable per call (default `"BARQ"`), satisfying "sequential or configurable." The sequence is never reset per year; the year in the number is a readability aid, not a per-year counter.

## 5. Template Engine

Three concrete templates today (`STANDARD_SERVICE`, `PREMIUM_SERVICE`, `CORPORATE`), selected by `getContractTemplate(key)` — the one factory function that branches on template key, mirroring Phase D.4's `getOtpProvider()` pattern exactly. Adding a template is: implement `ContractTemplate`, add one `case` to the factory. `GOVERNMENT` (requirement #4's explicitly named future template) is a recognized key that throws a clear, distinct error today rather than silently falling back to the wrong template.

**All current template wording is placeholder, generic boilerplate** — clearly not final legal text, appropriate to a phase explicitly marked "NOT the final electronic signature implementation." No governing document in this repository defines BARQ's actual contract language; a future legal/business review replaces the wording inside `service-templates.ts` without touching the template *mechanism* (parameterized rendering, versioning, factory selection) this phase actually delivers.

Content is bilingual JSON (`{ ar, en }` per section), matching the exact storage convention ADR-0005/`PRISMA_SCHEMA.md` already establish for `Service.name` etc.

## 6. Booking Integration — Prepared, Not Wired

Requirement #6: *"BookingAccepted -> Contract Generated. Only prepare the integration. Do NOT automatically generate contracts yet."* This phase's Critical Rules also say *"DO NOT: Change Booking Lifecycle."* Both are satisfied the same way:

- `createContractFromBooking()` (`src/lib/contracts/create-contract.ts`) is fully built and tested — it's exactly what a future call from `src/lib/booking/lifecycle/hooks.ts`'s `onAccepted()` would invoke.
- **`onAccepted()` itself was not touched this phase.** It remains its Phase E.1 empty stub (`void ctx;`). Wiring the two together in a future phase is a one-line addition inside that function's body — not a redesign of either engine.

## 7. PDF Architecture

`ContractPdfGenerator` is a small interface (`generate(content, meta): Buffer`), not a single hardcoded implementation — a future phase can swap in a real branded/styled generator (headless-browser rendering, a proper PDF library, a third-party API) without any caller of `generateContractPdf()` changing.

The default implementation, `simple-pdf-writer.ts`, hand-rolls valid PDF bytes directly (header, Catalog/Pages/Page/Font/Content objects, xref table, trailer) — no new npm dependency, consistent with this codebase's established minimal-dependency preference (e.g. Twilio via plain `fetch` in Phase D.4). "Do NOT focus on visual styling" is taken literally: one font (Helvetica), one size, plain black text, simple pagination — "clean professional," not decorated. `ContractPdfMeta.branding` is a reserved, currently-unused field so a future implementation supporting logos/letterhead doesn't need a signature change.

**Known, deliberate limitation:** this writer only renders Latin (English) text. PDF's standard Type1 fonts have no Arabic glyphs, and correct Arabic PDF rendering requires an embedded Unicode font plus right-to-left text shaping — real engineering beyond "do not focus on visual styling." Rather than silently emit garbled bilingual output, `generate-contract-pdf.ts` renders only each section's `.en` text. A real, Arabic-capable PDF implementation is a natural next step, swapped in via the same `ContractPdfGenerator` interface.

## 8. Versioning & Archive (Immutability)

Requirement #5 ("Future edits must never overwrite history") and requirement #9 ("Contracts must remain immutable after generation... Never overwrite previous contracts") are the same guarantee, enforced the same way: **a contract's `content` is never UPDATEd.** `createContractRevision()` is the only way a contract effectively "changes":

1. Creates a brand-new `BookingContract` row: fresh `contractNumber`, `version = previous.version + 1`, `supersedesContractId` pointing at the row it replaces, status `DRAFT`.
2. Sets the *previous* row's `archivedAt` — and only that field. Its `content`/`status` are frozen at whatever they already were.
3. Logs a `CREATED` event on the new row and an `ARCHIVED` event on the old one.

This mirrors the pre-existing platform `Contract` model's own supersession self-relation (`supersedingContractId`/`supersededByContract`) rather than inventing a new versioning idiom. Revising an already-archived contract is rejected (`ArchivedBookingContractError`) — only the current, non-archived version may ever be revised, keeping the supersession chain linear rather than forked.

## 9. History

`getContractHistory(contractId)` reads `BookingContractEvent` rows, oldest-first — the same underlying data serves "Contract History" (requirement #8) directly. Like Phase E.1's Booking Timeline, the raw `actorId` is deliberately excluded from the returned DTO; `actorType` (role) is what this requirement asks for, not an internal identifier.

## 10. Future Extension Points

`src/lib/contracts/extensions/future-extensions.ts` — pure TypeScript interfaces, zero implementation, zero runtime code:

- **`ElectronicSignatureProvider`** — `requestSignature()` / `verifySignature()`. Natural attachment point: `onIssued()` or `onActivated()` in `lifecycle/hooks.ts`.
- **`QrVerificationService`** — `generateVerificationCode()` / `verifyCode()`, for a printed contract's QR code resolving to a public authenticity check.
- **`ApprovalWorkflow`** — `requestApproval()` / `recordApprovalDecision()`, covering `GOVERNMENT`, `EMPLOYER`, and `CUSTOMER` approver types as one shared shape.

A future phase implements one of these, likely with its own `getXxxProvider()` factory (mirroring `getContractTemplate()`/`getOtpProvider()`), and wires it into a lifecycle hook — no change to `transitionContract()`, the transition matrix, or this file's interfaces required.

## 11. Deliberately Deferred Future Work

- Wiring `createContractFromBooking()` into `onAccepted()` (§6).
- Electronic signature, QR verification, and approval workflow implementations (§10) — interfaces only today.
- Real, styled/branded PDF output and Arabic-capable PDF rendering (§7).
- Final, legally-reviewed contract wording (§5) — current text is placeholder boilerplate.
- A `GOVERNMENT` template (§5) — reserved key, not implemented.
- Contract renewal (an `EXPIRED -> ACTIVE`-style transition) — deliberately not added to the matrix without a real feature defining its own rule (§3).
- Any new API route or Server Action exposing this engine to the UI — this phase built the library only.
